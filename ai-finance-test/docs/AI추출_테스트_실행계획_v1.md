# AI 추출 검증 테스트 — 실행 계획 (v1)

> **기준 문서**: `개발자공유_AI추출_테스트명세서.md`
> **실행 방식**: Python 스크립트 + LLM API 호출
> **대상 샘플**: A(레버리지·합성·환헤지) / B(커버드콜·액티브·월분배) / C(TDF·자산배분)
> **공유 대상**: 개발 / 기획 / 디자인 — 각 팀이 확인할 항목은 §8 참조

---

## 0. 이 테스트가 답하려는 질문

명세서의 원래 질문은 하나입니다.

> **투자설명서에서 필요한 항목이 실제로 추출되는가?**

여기에 이번 논의에서 두 개가 추가됐습니다.

> **(추가1) 추출된 값에 붙은 근거 원문이 실제로 문서에 존재하는가?**
> **(추가2) 투자설명서를 DART에서 자동으로 가져올 수 있는가?**

세 질문은 성격이 달라서 **하나의 실행에 섞으면 실패 원인을 못 가립니다.** 트랙을 나눕니다.

| 트랙 | 검증 대상 | 입력 | 실패 시 의미 |
|:--|:--|:--|:--|
| **A** | AI 추출 정확도·근거·재현성 | **수동 다운로드 PDF (고정)** | 서비스 성립 불가 → 전처리/프롬프트 재설계 |
| **B** | DART 자동 수집 경로 | DART OpenAPI | 자동화만 불가 → 수동 확보로 MVP 진행 가능 |

**트랙 A의 입력은 반드시 고정된 로컬 PDF입니다.** 여기에 DART 조회를 끼워 넣으면, 값이 안 나왔을 때 "문서를 잘못 가져온 건지 AI가 못 읽은 건지" 구분이 안 됩니다. 트랙 B는 병렬로 돌리되 트랙 A의 입력에는 관여하지 않습니다.

## 1. 트랙 A — 실행 설계

### 1-1. 입력 조건 2가지

명세서 작업순서에는 "섹션 분할 전처리"가 들어 있는데, **비교 대상이 없으면 섹션 분할이 필요한지 아닌지 알 수 없습니다.** 두 조건을 나란히 돌립니다.

| 조건 | 내용 | 확인하려는 것 |
|:--|:--|:--|
| **C1** | PDF 전문 텍스트를 통째로 투입 | 전처리 없이 되는가 (되면 파이프라인이 대폭 단순해짐) |
| **C2** | 목차 기준 섹션 분할 후 관련 섹션만 투입 | 전처리가 정확도를 실제로 올리는가 |

### 1-2. 종목명 파싱 보정은 "실행 조건"이 아니라 "채점 후처리"입니다

명세서 §4의 보정 규칙표를 적용하면 종목명만으로 다음이 자동으로 채워집니다.

- A: `(합성)`→복제방식, `(H)`→환헤지여부, `레버리지`→전략유형 = **3점**
- B: `커버드콜`→전략유형, `액티브`→액티브여부 = **1점** (Tier1 기준)
- C: `TDF2045`→전략유형 + 목표시점 = **1점** (Tier1 기준)

즉 **AI가 아무 값도 못 내놔도 24점 중 5점 안팎이 자동으로 들어옵니다.** 보정을 켠 채로 채점하면 원래 질문("추출이 되는가")에 답할 수 없습니다.

> **규칙: 보정 전 원점수를 먼저 확정하고, 보정 후 점수는 같은 표의 별도 열에 기록합니다.** 판정(§5)은 원점수 기준입니다. 보정 후 점수는 "서비스에서 실제로 도달 가능한 정확도"로 별도 보고합니다.

### 1-3. 실행 규모

```
2 조건(C1, C2) × 3 샘플(A, B, C) × 3 반복 = 18 회 호출
temperature = 0, 동일 프롬프트, 동일 모델
```

반복 3회는 정확도가 아니라 **재현성**을 보기 위한 것입니다. temperature 0인데도 값이 흔들린다면, 규칙 엔진 입력값으로 쓸 수 없고 캐싱 설계도 달라집니다.

### 1-4. 프롬프트 설계 원칙

- 출력은 **명세서 §3 스키마 그대로**, JSON 외 텍스트 금지
- enum 필드는 **허용값 목록을 프롬프트에 명시**하고 그 외 문자열 금지
- **모든 Tier1 필드에 대해 `근거원문` 동반 필수**
- **근거를 찾지 못하면 값을 추측하지 말고 `null` 반환** — 명세서 §2의 "근거를 못 찾으면 추출 실패로 처리" 원칙을 프롬프트 레벨에서 강제
- 문서에 없는 내용을 일반 지식으로 채우지 말 것을 명시 (예: "TIGER TDF2045는 보통…" 같은 사전지식 차단)

`null` 반환은 오답이 아니라 **정직한 실패**로 별도 집계합니다. 서비스 관점에서 "모른다고 말하는 실패"와 "틀린 값을 자신 있게 내놓는 실패"는 위험도가 완전히 다릅니다.

## 2. 채점 규칙

### 2-1. 정답지부터 확정 (선행 작업)

`총보수` B·C가 "확인필요"로 비어 있습니다. 이 상태면 만점이 24가 아니라 **22**인데 합격선은 "22개 이상(91%)"으로 잡혀 있어 계산이 성립하지 않습니다.

**선택지 (착수 전 결정 필요):**
- (a) B·C 총보수를 확정 → 만점 24 유지
- (b) 총보수 필드를 이번 테스트에서 제외 → 만점 21 (7필드×3), 합격선 19개(91%)로 재계산

→ **권장은 (a)**. 총보수는 서비스 화면(핵심 상품 구조 명세 테이블)에 이미 들어가 있는 필드라, 어차피 정답을 알아야 합니다.

### 2-2. 필드별 정답 판정 기준

채점자 재량이 들어가면 결과를 못 믿습니다. 실행 **전에** 다음을 고정합니다.

| 필드 | 판정 방식 |
|:--|:--|
| `종목명` | 공백·괄호 정규화 후 완전일치 |
| `기초지수` | 샘플별 **허용 문자열 목록**을 사전 작성 후 매칭<br>예) A: `S&P 500`, `S&P500`, `S&P 500 지수` 모두 정답 |
| `레버리지배율` | 수치 완전일치 (2.0 == 2) |
| `복제방식`·`환헤지여부`·`전략유형`·`분배정책` | **enum 완전일치**, 표기 흔들림 불허 |
| `총보수` | 소수점 2자리 완전일치 |

enum 4개를 완전일치로 잡는 이유: 이 값들은 사람이 읽는 게 아니라 **규칙 엔진의 입력 키**로 그대로 들어갑니다. `"합성복제"`처럼 조금만 달라도 규칙 매칭이 실패하므로, 테스트 단계에서 관대하게 채점하면 안 됩니다.

### 2-3. 근거 원문 자동 검증

사람 눈 대조는 3샘플 × 8필드 × 3반복 × 2조건이면 현실적으로 불가능합니다. 자동화합니다.

```
1) PDF 전문 텍스트를 공백·줄바꿈·특수문자 제거하여 정규화
2) AI가 반환한 근거원문도 동일하게 정규화
3) 부분일치(substring) 검사
4) 실패 시 → 앞뒤 10자씩 잘라 재시도 (앞뒤 잘림 대응)
5) 그래도 실패 → evidence_found = 0 (지어낸 인용으로 분류)
```

**`evidence_found = 0`인 필드는 값이 맞았더라도 별도 표시합니다.** 값은 맞았는데 근거가 허구라면, 서비스의 신뢰 장치(근거 원문 패널)가 무너진다는 뜻입니다.

### 2-4. 함께 측정하는 항목

명세서에는 없지만, 화면 시안이 이미 전제하고 있는 값들이라 같이 기록합니다.

| 항목 | 왜 필요한가 |
|:--|:--|
| **응답 소요시간(초)** | 로딩 화면 카피 "보통 10초 이내로 완료됩니다"가 지킬 수 있는 약속인지 |
| **페이지 번호 / 조항 번호 추출 여부** | 근거 패널의 "P. 42 / 제2부 9-나" 표기가 자동으로 채워지는지 |
| **입력 토큰 수** | C1(전문) 방식의 비용·컨텍스트 한계 확인 |
| **3회 반복 간 값 동일 여부** | 캐싱 설계 및 "판단은 규칙, 추출은 AI" 주장의 근거 |

## 3. 기록 스키마

결과는 두 개의 CSV로 남깁니다. 나중에 심사 제출용 근거 자료로 그대로 씁니다.

**`runs.csv`** — 실행 단위
```
run_id, timestamp, model, condition(C1|C2), sample(A|B|C), repeat(1-3),
latency_sec, input_tokens, output_tokens, json_parse_ok, raw_response_path
```

**`results_field.csv`** — 필드 단위
```
run_id, sample, field, ai_value, expected_value,
match_raw(0|1), match_corrected(0|1), is_null(0|1),
evidence_text, evidence_found(0|1), evidence_page
```

디렉터리 구조 제안:
```
/test
  /pdfs           A.pdf B.pdf C.pdf (고정, 절대 수정 금지)
  /text           전문 텍스트 추출 결과
  /sections       C2용 섹션 분할 결과
  /raw            18개 응답 JSON 원문
  /prompts        사용한 프롬프트 (버전 고정)
  ground_truth.json
  runs.csv
  results_field.csv
```

## 4. 트랙 B — DART 수집 경로 검증

### 4-1. 확인 항목

명세서 §7의 3가지 미확인 사항을 그대로 체크리스트화합니다.

- [ ] 미래에셋자산운용 `corp_code` 확보 (corpCode.xml 전체 다운로드 후 검색)
- [ ] `list.json` 공시 목록 조회 → **`report_nm` 실제 표기값 수집**
      (`투자설명서` / `[정정]투자설명서` / `간이투자설명서` 중 무엇이 오는지)
- [ ] **공시 단위 확인**: ETF 종목별인가, 운용사/펀드 단위 묶음인가
      → 종목명 검색으로 도달 가능한지, 아니면 문서 내부에서 해당 ETF를 찾아야 하는지
- [ ] `document.xml` 응답 ZIP 내부 포맷 (XML인지 PDF인지, 문서마다 다른지)
- [ ] **A·B·C 3종 모두 자동 도달 가능한가** (성공률 3/3인지)
- [ ] 정정 공시가 여러 건일 때 최신본 판별 규칙
- [ ] 수집한 문서가 수동 다운로드본과 **동일한 문서인지** 대조

### 4-2. 판정

| 결과 | 다음 조치 |
|:--|:--|
| 3/3 도달 + 포맷 일관 | 자동 수집 배치 구현 |
| 부분 성공 | 반자동 — 종목별 문서 URL 매핑 테이블 + 갱신 감지만 자동화 |
| 실패 | MVP는 수동 확보, 기획서에는 "확장 계획"으로 기술 |

### 4-3. 아키텍처 권고 — 실시간 조회가 아니라 사전 캐시

트랙 B 결과와 **무관하게**, 서비스 런타임에서 DART를 직접 조회하는 구조는 권하지 않습니다.

- 투자설명서는 정정 시에만 갱신됩니다. 실시간성이 필요한 데이터가 아닙니다.
- MVP 대상은 3~4종 고정입니다.
- DART API 장애·레이트리밋이 곧바로 서비스 장애가 됩니다.
- 수십 페이지 PDF 다운로드 + 파싱 + AI 추출을 요청 시마다 하면 "10초 이내" 약속을 못 지킵니다.

**권장 구조:**
```
[배치] DART 조회 → PDF 확보 → 텍스트 추출 → AI 추출 → SQLite 저장
                                                        ↓
[런타임] 사용자 요청 → SQLite 조회 → 규칙 엔진 → 화면 출력
```
DART는 **수집 배치에서만** 사용합니다. 기획서에는 "자동 수집 파이프라인 + 캐시 계층"으로 서술하면 확장성 주장도 그대로 유지됩니다.

> ⚠️ **기획·디자인 확인 필요**: 사전 캐시 구조면 결과가 즉시 나옵니다. 그런데 로딩 화면(5번 시안)은 "투자설명서를 불러오고 있습니다 → 위험 구조를 확인하고 있습니다"를 순차 표시합니다. 실제로 그 순간 일어나지 않는 일이라면, 우리가 문제 삼는 **다크패턴 논리와 충돌**합니다. 로딩 연출을 유지할지, 캐시 시점을 명시(예: "2026-08-20 기준 투자설명서")할지 결정이 필요합니다.

## 5. 판정 기준 (재정의)

**분모: Tier1 8필드 × 3샘플 = 24 (총보수 B·C 확정 전제)**
**기준 점수: 종목명 파싱 보정 적용 전 원점수**

| 결과 | 판정 | 다음 단계 |
|:--|:--|:--|
| 22개 이상 (91%) | 성공 | Tier2 확장 + 트랙 B 결과 반영 |
| 18~21개 | 조건부 | 오답 필드 분석 → 프롬프트 또는 섹션 분할 개선 후 재테스트 |
| 17개 이하 | 실패 | 전처리 재설계 |

**추가 통과 조건 (기존 정량 기준과 별개로 모두 충족해야 함):**
- 근거 실재성: 정답 처리된 필드의 **`evidence_found` 90% 이상**
- 재현성: 3회 반복 시 Tier1 필드값 **불일치 0건**
- 실패 방식: 오답 중 "틀린 값을 자신 있게 반환"보다 `null` 비율이 높을 것
